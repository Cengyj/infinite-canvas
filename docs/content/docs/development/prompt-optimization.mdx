# Prompt Optimization Design

Prompt optimization shares one workflow across the image workbench, video workbench, canvas image/video nodes, and their generation-config composer. Users select a text model, edit the source and additional requirements, inspect streamed output, and explicitly apply the result. Applying replaces the prompt without starting image or video generation.

Workbench prompt actions follow the earlier workbench layout: a small prompt label followed by three equal-width, equal-height outlined buttons, ordered Prompt library, View assets, Optimize prompt. The three-column grid uses compact 12px labels and narrow gaps to fit the 420px desktop column. Below 390px, icons disappear while labels remain visible.

Canvas image/video nodes follow the earlier entry layout: a 32px wand icon button sits in the regular prompt panel's bottom toolbar after Prompt library and before model selection, without a separate row. The expanded editor has an icon and text action on the right of its title, opening optimization after the editor's closing animation finishes. Both entries permit empty drafts; config composers keep their existing entry.

An earlier source review confirmed that image/video optimization and model presets already existed in the pre-rollback backup, with matching entry points and presets. That review fixed existing gaps in context, image numbering, editor interaction, and configuration persistence within the same optimization flow.

## Official sources and model boundaries

This section preserves an earlier official-documentation review. The current review did not retrieve the official model documentation again; these records are not a claim of current revalidation, provider availability, or real-model quality acceptance.

The earlier review of the [GPT-6.1 Sol model page](https://developers.openai.com/api/docs/models/gpt-6.1-sol) recorded text and image input and text output for the exact model `gpt-6.1-sol`. The reviewed [reasoning guide](https://developers.openai.com/api/docs/guides/reasoning) included Responses API examples for this model and listed `low`, `medium` (default), `high`, `xhigh`, and `max`, with `none` and `minimal` unsupported. The reviewed [Responses request reference](https://developers.openai.com/api/reference/resources/responses/methods/create) did not list `auto` for `reasoning.effort`. The interface's automatic setting means omitting effort so the model uses its default; explicit settings send their corresponding value. `auto` in `reasoning.context` or `reasoning.summary` is a different setting.

The earlier review of the [image-input guide](https://developers.openai.com/api/docs/guides/images-vision) and request reference recorded `input_text` and `input_image` content blocks for Responses, with a fully qualified URL or base64 data URL in `image_url`, or a `file_id`. Internal application message blocks must be converted at the request layer rather than sent unchanged to Responses.

The earlier review recorded the model page's link to the [GPT-6 guide](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-6-astra#gpt-61-sol). Its Prompting best practices section offered a starting point for evaluation across the family, explicitly based on Astra observations requiring evaluation with the chosen model and workload. This design uses clear output formatting, explicit instruction priority, and less stock phrasing without claiming demonstrated Sol quality. Official capability documentation does not establish availability or compatibility for the configured provider, proxy, or account; rewrite quality still needs manual acceptance.

| `services/api/image.ts` | Reuses OpenAI, Gemini, and custom text scripts with complete-result checks for optimization |

Each entry provides `getInput` and `onApply`. Opening captures the current input; edits inside the dialog affect only the optimization request. Applying reads and compares the current input again before calling the editor's existing update action. Shared providers and the text model come directly from the existing configuration store.

An empty source is allowed when opening the dialog, and opening sends no request. Users can enter their initial draft inside it; a nonempty source is required only before starting an optimization request. Canceling still leaves the original editor unchanged.

Sessions, source drafts and results live only in component memory. Closing does not create draft/result history. Only explicitly saved additional requirements have their own localforage storage, separate from optimization sessions. Applied prompts follow the existing workbench/canvas persistence behavior. API keys remain in browser storage, and requests use the existing direct route or explicitly enabled local proxy. Built-in OpenAI text requests send `store: false`; custom scripts control their own requests.

## Reusable additional requirements

The requirements picker offers a few image/video suggestions and favorites saved explicitly by the user. Selecting an item appends it to existing requirements for further editing; selecting the same complete requirement again does not duplicate it. Image favorites do not appear in video sessions, and vice versa. Opening a dialog never applies a favorite automatically. Saving/deleting a favorite does not change the current draft or output. The built-in “Shorten without expanding” suggestion explicitly forbids new visual details, actions, subjects, styles or story events; changing this suggestion does not rewrite user favorites.

The store uses `infinite-canvas` / `prompt_optimization_requirements`, storing each scenario/text pair separately. A read/write failure is reported without clearing current text or treating an unsuccessful write as saved; invalid stored records are not overwritten. Requirement changes reuse the existing result signature and require re-optimization before application. The `opentu` comparison informs requirement reuse and restrained development of useful visual elements. The existing scenario and edit constraints remain authoritative; this does not add a knowledge base, JSON output, automatic prompt history, or new model settings.

## Context and references

- **Separate draft and upstream text:** the editable draft is `prompt`, while connected text becomes read-only `upstreamText`. Instructions tell the model to use this context without copying it into the result, avoiding repeated `【Text N】` blocks during generation.
- **Generation and optimization models are separate:** `generationModel` describes the target image/video model and its OpenAI, Gemini, or script transport; `textModel` performs the rewrite. Optimization does not switch the generation model or mechanically insert model names and parameters into the prompt.
- **Generation system instructions:** image context includes the configured `systemPrompt` as read-only `generationSystemPrompt`. Optimization accounts for these constraints without copying them into the draft or treating them as instructions to override its output contract. Snapshot comparison includes the field, so changes invalidate old results.
- **Gemini image size:** built-in requests and optimization share `resolveGeminiImageConfig`. Context uses effective `aspectRatio` and `imageSize` as `frameSize` and `resolution` instead of claiming that raw pixels or an input ratio are the final request parameters. Parsing and limits were extracted unchanged; incomplete edits omit unresolved fields while generation retains its existing validation. Saved scripts keep their own input contract.
- **Native Gemini image quality:** omit `quality`, which the native image request does not submit; changing only this unused setting does not invalidate output. Effective `imageConfig` ratio/resolution changes still do. OpenAI and saved scripts retain their existing quality semantics. The shared UI still permits transparent background, so its user intent remains in optimization context without claiming that native Gemini receives a background API parameter.
- **Effective video settings:** generation and optimization share resolveVideoGenerationConfig. Non-Grok models/scripts retain their modes/duration rules without inferring script internals. Built-in Grok follows current provider documentation and completed requests with model/prompt/seconds/aspect_ratio/resolution/reference_images. frameSize is the submitted aspect_ratio and quality is resolution, not an exact pixel-size promise. Zero images means text-to-video and 1–7 means ordinary references, ignoring legacy mode. The approved shared rule allows 1.5 1080p for zero/one ordinary reference, while two through seven remain limited to 480/720p; classic duration/resolution rules are unchanged. Invalid multi-image 1080p is a resolution issue, not a reason to invent a first-frame role or lower resolution. Valid 1/3 seconds stay unchanged. Images use reference-image/reference; no images means no frame roles. Omit invalid executable conditions; read-only generationIssues must not enter prose or induce invented settings. Grok omits audioEnabled, which does not mean false, audio control or guaranteed silence; rejected audio/video inputs are not usable references. Gemini describes only its first actual audio/video input; image rules remain separate.
- **Separate Grok provider evidence from local policy:** yuanai.uk key-boundary sampling completed no-image, single-image, seven-image and short/upper-duration cases, with explicit rejections for unsupported classic resolution/duration, 1.5 multi-image 1080p, eight images and sixteen seconds. Four real project-service calls completed seven-image/one-second classic/1.5 requests at 480/720p without mocks. The old balance block is resolved; this is not exhaustive combination or quality acceptance. The user has since approved and the project now implements 1.5 1080p for zero/one ordinary reference; two through seven images remain disabled at 1080p. These earlier provider results are not new paid generation or current behavioral-regression results. No first-frame mode was tested; browser workflows remain pending. See the [Grok plan and evidence](/docs/progress/grok-video-frontend-plan).
- **Image intent and roles:** `imageIntent` marks `create`, `reference`, or `edit` participation. The `edit` label requires the source image in the actual reference list; an existing image node or ordinary references alone do not establish source-image participation. `imageRoles` follows actual order with `source-image`, `reference-image`, `first-frame`, or `last-frame` and remains in internal context and snapshot comparison. Requests include roles only in `referenceImages[].role` and labels preceding actual images, without repeating them inside `generationContext`. These technical roles do not invent artistic purposes such as style or composition. In particular, `source-image` and the `edit` participation label do not restrict the task to a local edit; the requested outcome determines the permitted scope.
- **Regular nodes:** the `@` menu, Image N labels, and optimization references follow the actual generation order. Creating a new result prepends the source only when it has image content. Overwrite does not add it automatically, but a source explicitly referenced through a group or connection keeps its actual position and receives `source-image` / `edit` when the final deduplicated references contain that image node. Numbering reuses generation input parsing, including group expansion, deduplication, and connected-config priority, without rewriting existing draft text.
- **Config nodes:** a nonempty composer selects inputs through `@[node:id]` tokens. Group tokens expand valid children and deduplicate node IDs. Without composer content, implicit inputs become an explicit token draft only in the optimization snapshot until the user applies it.
- **Stable tokens:** results preserve every distinct token and its first-appearance order. Repetition is allowed, but changing IDs, removing/adding tokens, reordering first appearances, or substituting labels is rejected. The dialog displays readable chips; selected-text copy/cut writes original `@[node:...]` tokens to the clipboard. Cutting a read-only result does not delete it.
- **Image analysis is off by default:** disabled analysis sends labels, names, and roles without inferring visual contents from filenames. Enabling it loads original images in actual order and sends them with labels and roles. Video/audio references provide names only; their media is not supplied for analysis.
- **Local generation identity:** generationIdentity compares model, provider, protocol, URL, script and raw config.size locally; video adds raw videoSeconds and vquality. Grok excludes legacy videoMode/videoGenerateAudio/videoWatermark, so those alone do not stale output; other models/scripts retain them. Relevant raw-value changes still stale output when invalid, omitted or resolved identically. Identity is never sent to the optimizer, and invalid settings do not become executable conditions.

## Rewrite contract and text requests

The service applies a shared contract followed by image or video rules. The shared contract preserves language, subject identity and count, explicit exclusions, and visible wording including quotation marks, punctuation, and requested line breaks. New additional requirements override creative details only where they explicitly conflict, never the token contract. Source material and upstream content are creative data rather than instructions to change the output contract.

Development follows semantic completeness, considering upstream text, generation instructions and actual reference roles, rather than character count. A short edit request may already be complete.

- Open creation ideas receive a small, coherent set of useful presentation choices, such as framing, light and texture; optimization should do more than add a quantity word or punctuation. This does not authorize new subjects, unsupported breeds or identities, visible wording, named styles, locations or story events. Categories are not a mandatory checklist, and output has no fixed word-count target.
- Specific prompts receive light clarification and organization without replacing their decisions or adding redundant description. Explicit brevity, minimal rewriting or no-expansion requirements take precedence.
- Local editing stays within the requested change and names what remains. A background-only edit must not redesign, reframe or relight the subject. Explicit overall restyling, recomposition or re-creation allows the coherent composition, light, palette and material changes needed for that outcome, while retaining identity, count, visible wording and other unchanged anchors.

Image rules distinguish reference-free creation, reference-guided creation, local edits and broader transformation. Useful framing, light and spatial decisions follow the subject and intended use; close-ups, soft light and blurred backgrounds are not universal defaults. Source participation does not freeze attributes the requested transformation needs to change. Exact visible wording, transparency and unaffected anchors remain protected. Reference purposes and numbering follow actual input; analysis-off references do not reveal unseen appearance or purpose.

Video rules develop an existing action into a feasible continuous progression with clear pace, movement direction and spatial continuity. A bare subject does not authorize a new action or plot. Subject movement and camera movement remain separate: a fixed camera keeps its position, direction and framing unchanged, with subject motion described relative to that fixed view and no following/tracking language. Short clips do not gain cuts, extra scenes or a forced ending. Actual first/last-frame roles and ordinary references remain distinct; analysis-off references do not justify invented appearance or endpoints. Explicit sound constraints and the effective audio switch remain authoritative.

The refinement stays within the existing service, dialog and context layers. It adds no UI mode, character-count gate, request path, model/reasoning setting or retry/timeout behavior.

The model is instructed to return only a usable prompt body without explanation, headings, JSON, code fences, or extra enclosing quotation marks. Code trims surrounding whitespace without heuristically stripping quotation marks or fences, which could damage requested visible text; output-format compliance is part of manual acceptance. Parameters constrain composition, pacing, and output conditions without mechanically filling photography categories or guessing roles from filenames and unanalyzed media.

Newly loaded OpenAI/Gemini default text-script templates correct image/text conversion, request paths, complete-result validation, and refusal handling. They do not automatically overwrite saved user scripts. Saved scripts remain user-controlled and must not be assumed to inherit template fixes. Native Gemini text requests filter content marked `thought`, passing only answer text to optimization.

## Applying, invalidation, and cancellation

The shared dialog footer keeps all buttons on one right-aligned row: Cancel → Start/Re-optimize (Stop while requesting) → Refine from result (when a result exists) → Apply to prompt. Optimization actions remain to the left of Apply; very narrow windows retain horizontal scrolling. Button handlers and disabled-state rules are unchanged.

Only complete, nonempty output with valid tokens can be applied. The ready status uses the same apply eligibility: clearing the result or changing its tokens shows an inapplicable state instead of a ready checkmark. Built-in OpenAI/Gemini requests require a valid completion state. Truncated, refused, failed, or interrupted responses cannot become applicable output. Custom text scripts must finish normally and return text.

A session belongs to the current workbench session or canvas project/node. Changes to the source, reference order/content, upstream text, generation system instructions, raw image size or effective ratio/resolution, reference mapping, or generation context invalidate its snapshot; users can reload the current input. The dialog checks the actual resolved text provider and rechecks the latest model and source snapshot when a delayed response completes, rather than comparing only the global default provider. Unavailable models require configuration instead of silently selecting another provider.

Each complete result records its request source. Manually changing the left source disables both refinement from the old result and application, so the old result cannot silently replace the new draft. Restoring the exact recorded source restores eligibility when all other checks pass. Failure or stopping a new-source request keeps that new draft and the previous complete result, without making the old result applicable.

When the source is unchanged, changing only additional requirements, the selected valid text model or reference analysis still allows refinement from the previous complete result, but not direct application. The next request uses that result with the current settings. Failure or cancellation retains the previous complete result and restores the source present before the request; snapshot, token and model-readiness checks continue to apply.

Stopping, closing, unmounting the editor, invalidating the source, or changing text-model configuration cancels the request. Late chunks cannot update the preview. Stopping or failing preserves the previous complete result rather than applying partial output. Regular nodes reuse `updatePrompt` to update local editor state and metadata together; config nodes receive the raw token draft. No additional binding affects later generation after application.

Keyboard events inside the optimization dialog are isolated from canvas shortcuts, preventing text editing from also deleting, undoing, or selecting canvas nodes. Space/Control in dialogs, editable fields and requirement popovers cannot temporarily switch the canvas tool; ordinary canvas shortcuts remain available outside them. Escape retains normal dialog behavior. Copy/cut serializes selected raw tokens; paste accepts plain text, and application still requires complete-result and reference validation.

## Four real text samples

After the user configured the Chrome incognito session, a separate product tab completed exactly four real text-optimization requests; all four reached Result ready. The visible text-model label was gpt-6.1-sol（OpenAI）. Additional requirements were empty, reference analysis was off, and the reference count was zero in every request. Image-generation context was gemini-3.1-flash-image-preview at 1024x768; the video-generation context was grok-imagine-video-1.5 at 5 seconds, 720p and 4:3. These generation models were context only: no image or video generation was requested. No result was applied, and the channel, models, parameters and original user draft were not changed. The temporary tab was closed while the user’s original page remained open.

The following inputs and outputs are actual text results, copied verbatim; their Chinese bodies are intentionally unchanged in both language versions. This is a four-case text-quality sample, not acceptance of all 30 illustrative cases, finished-image/video evaluation, or a controlled A/B comparison with opentu. Local evidence is stored in /tmp/infinite-canvas-prompt-live-results.json and /tmp/infinite-canvas-prompt-live-{1,2,3,4}.png.

### 1. Open kitten idea

Original input:

```text

```

```text
以小猫为画面主体，采用自然的近景构图，突出清晰的面部表情、眼神和柔软毛发的细腻层次。使用柔和、均匀的光线塑造立体感，背景简洁并适度虚化，将视觉重点集中在小猫身上，整体氛围温暖自然。
```

```text
文字内容、中文引号、冒号与空格逐字保留，不添加其他文字、道具或装饰。
```
